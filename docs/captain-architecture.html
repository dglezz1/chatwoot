📥 3 paths que disparan Captain desde un mensaje entrante

Path A · Hook path (la ruta histórica)

Webhook → Message#execute_message_template_hooks → MessageTemplates::HookExecutionService#trigger_templates:

  • → super() ejecuta greeting / OOF / email-collect (OSS templates)
  • → captain_safe_to_respond? valida: pending + incoming + !@g.us + captain_assistant + captain_active
  • → schedule_captain_response encola ResponseBuilderJob
  • → el job bifurca: V1 (AssistantChatService one-shot) o V2 (AgentRunnerService con tools)
  • → post-process: ClassifierActionService + FalsePromiseService
  • → al final envía via Messages::MessageBuilder → SendReplyJob → OpenWA

Path B · Listener path (ruta V2 moderna, dos etapas)

EventDispatcher (message_created) → CaptainListener → Captain::AutoReplyJob (debouncer con Redis SETNX) → Captain::DelayedAutoReplyJob.set(wait: rand(15..45).seconds):

  • ⏱ Debounce: múltiples mensajes del mismo contacto colapsan en 1 reply
  • ⏱ Delay aleatorio para evitar bot-detection de WhatsApp
  • ⏱ Después del delay, espera extra debounce_window_seconds (~20s) para acumular stragglers
  • Modo off → no-op · welcome_only → canned · ai → AgentRunnerService
  • Si handoff keyword match → mándale mensaje de handoff y para (no más replies)

Path C · Cron path (auto-resolve)

config/schedule.yml cada 5 min → TriggerScheduledItemsJob → Account::ConversationsResolutionSchedulerJob → Enterprise::Account::ConversationsResolutionSchedulerJob → Captain::InboxPendingConversationsResolutionJob (one per inbox):

  • Para conversaciones idle más de 1 hora…
  • V2 con captain_tasks: LLM evalúa si está completa → resuelve o handoff
  • V1 / sin tasks: cierra directo con resolution_message

🧠 El Agente — V1 vs V2

V1 · Single-shot

AssistantChatService#generate_response → LLM en una sola llamada.

Post-process: AssistantActionClassifierService (label intent) + AssistantFalsePromiseService (catch "te aviso…" patterns).

enterprise/app/services/captain/llm/assistant_chat_service.rb

V2 · Tool-calling agent loop

AgentRunnerService usa el gem agents (RubyLLM). Construye un Agents::Runner con el assistant + cada scenario como agente, todos con tools compartidas.

runner.run(message, context: ..., max_turns: 100) corre el loop: el LLM decide tool → ejecuta → repite hasta final_answer.

  └─ Captain::Documents::CrawlJob

  └─ ResponseBuilderJob
       └─ LLM summarize → Captain::Document.content (chunked)
       └─ LLM::UpdateEmbeddingJob per chunk
       └─ EmbeddingService (vector)

⚙️ Configuración & quotas

Per-account quota

Account.usage_limits[:captain][:responses][:current_available] — decrementa en cada reply exitoso.

Feature flags

captain_integration (V1 + V2 visible en UI), captain_integration_v2 (tool-calling V2), captain_custom_tools, captain_tasks, captain_document_auto_sync

LLM endpoint

InstallationConfig.CAPTAIN_OPEN_AI_ENDPOINT, ..._MODEL, ..._API_KEY. Fallback a CaptainIntegrationService::LLM_CONFIG.

🛡 Guards de seguridad que PREGUNTAN al bot

Guard layer · Post-fix

  • captain_safe_to_respond? — central allow-list (aplicada en 3 lugares: Hook, Listener, Job)
  • 🚫 WhatsApp @g.us y @broadcast — nunca auto-reply a grupos (bug del 2026-07-03)
  • 🚫 Mensajes privados / vacíos
  • 🚫 Conversaciones asignadas a humano
  • 🚫 Inbox sin captain_assistant o sin quota
  • 🎯 recoverable_llm_error? — solo handoff en errores esperados (Faraday / Timeout / RateLimit / ContextLimit). Hard parse errors log silencioso.

📚 Tasks del dashboard (no auto)

  • Copilot — chat de preguntas del agente al LLM
  • Reply suggestion / Summary / Rewrite — tareas one-shot via lib/captain/*_service.rb
  • Label suggestion, Follow up, CSAT analysis — pre-fills para el agente
  • Article writer / translation / Help Center curation / Widget tagline — generación de contenido
